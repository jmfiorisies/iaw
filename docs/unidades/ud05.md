## 📖 0. Fundamentos: el cocinero de la casa

### 0.1 Recordamos el restaurante

| En el restaurante | En el servidor |
|---|---|
| El cliente | El navegador |
| El camarero | Nginx: recibe el pedido, sirve lo que ya está hecho (estáticos) y pasa el resto a la cocina |
| La cocina | El programa que genera la página: en la UD4, PHP-FPM; ahora, **Gunicorn + Flask** |
| La receta | El código (`.php` en la UD4, `app.py` ahora) |
| El plato | El HTML (o el JSON) que vuelve al navegador |

### 0.2 La diferencia que lo cambia todo

PHP y Python se ejecutan de forma distinta en el servidor, y eso tiene consecuencias para quien lo administra:

| | PHP (UD4) | Python (UD5) |
|---|---|---|
| Cómo trabaja | **Lee la receta en cada pedido**: cada petición ejecuta el `.php` desde el principio | **Se sabe la receta de memoria**: Gunicorn carga `app.py` una vez, al arrancar, y la deja en memoria |
| Si cambias el código | Se nota en la siguiente petición | **No cambia nada hasta que reinicias la app** |
| Los datos en memoria | Se pierden al acabar cada petición | Duran mientras la app está encendida (en el laboratorio, las recomendaciones) |
| Cómo habla con Nginx | FastCGI (`fastcgi_pass php:9000`) | **HTTP** (`proxy_pass http://app:8000`) |

!!! warning "La regla de oro de esta unidad"
    Si cambias `app.py`, la configuración de Gunicorn o las variables de entorno: **`docker compose restart app`**.
    En un servidor sin Docker, `sudo systemctl restart club`. Si no reinicias, Python sigue con la receta antigua.

| Pieza | Qué es | En el laboratorio |
|---|---|---|
| **Nginx** | Servidor web y proxy inverso: TLS, ficheros estáticos y reenvío de peticiones | Contenedor `nginx` |
| **Gunicorn** | Servidor de aplicaciones para Python: arranca varios procesos (*workers*) con la app y les reparte las peticiones | Contenedor `app`, puerto 8000 |
| **Flask** | Librería (*framework*) para escribir aplicaciones web en Python: rutas, plantillas, sesiones | `club/app.py` |
| **WSGI** | El «idioma» estándar con el que Gunicorn le pasa cada petición a Flask (PEP 3333) | No se configura: viene hecho |

¿Por qué no Flask solo? Flask trae un servidor de pruebas (`flask run`) que atiende **de una en una** y no está hecho
para producción. Gunicorn arranca varios workers, los vigila y los reinicia si se cuelgan. ¿Y por qué Nginx delante?
Porque Gunicorn no hace TLS ni sirve estáticos con eficiencia, y no conviene exponerlo a internet.

## 🔌 2. La regla para el camarero: `proxy_pass`

### 2.1 Las líneas

```nginx
location / {
    try_files $uri @app;        # si el fichero existe, lo sirve Nginx; si no, a la app
}

location @app {
    proxy_pass http://app:8000;                                     # contenedor «app», puerto de Gunicorn
    proxy_set_header Host              $host;                       # el nombre que pidió el cliente
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # la IP de verdad del cliente
    proxy_set_header X-Forwarded-Proto $scheme;                     # si entró por https
}
```

Léela en castellano: **«si está en la estantería, lo das tú; si no, a la cocina de `app:8000`»**.

- `try_files $uri @app;` prueba primero si existe el fichero (`estilo.css`, `hola.txt`). Si no existe, salta a la
  *location* con nombre `@app`. Una *location* que empieza por `@` no se puede pedir desde fuera: solo sirve de destino.
- `proxy_pass` es el mismo que en la UD3 (proxy inverso hacia Apache). Aquí el «servidor de detrás» es Gunicorn.

| UD4 · PHP | UD5 · Python |
|---|---|
| `location ~ \.php$ { … }` | `location @app { … }` |
| `fastcgi_pass php:9000;` | `proxy_pass http://app:8000;` |
| `include fastcgi.conf;` (`SCRIPT_FILENAME`) | `proxy_set_header …` |
| Nginx y PHP ven los ficheros en la misma ruta | La app **no necesita** ver los estáticos |

### 2.2 ¿Quién eres? Las cabeceras `X-Forwarded-*`

A la cocina solo le habla el camarero. Sin cabeceras, la app cree que **el cliente es Nginx** y que todo llega por
`http` (entre Nginx y Gunicorn no hay TLS). Salida real del laboratorio, sin las dos cabeceras:

```text
Tu IP: 172.31.0.3 · Has entrado por: http          ← 172.31.0.3 es la IP de Nginx en la red interna
```

Con `X-Forwarded-For` y `X-Forwarded-Proto` (y `nginx -s reload`):

```text
Tu IP: 172.30.0.3 · Has entrado por: https         ← la del cliente de verdad
```

¿Por qué importa? Los logs, los bloqueos por IP, los límites de intentos de login y las redirecciones a `https`
dependen de saberlo. La app tiene que **fiarse** de esas cabeceras solo si vienen de su Nginx; en el Club lo hace esta
línea de `app.py`:

```python
app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1)   # fiarse de UNA capa de proxy: la nuestra
```

### 2.3 En un servidor Debian (sin Docker)

```bash
sudo apt install nginx python3-venv
sudo python3 -m venv /srv/club/venv                 # un entorno aislado para las librerías de la app
sudo /srv/club/venv/bin/pip install flask gunicorn
```

Gunicorn se deja como servicio de systemd (`/etc/systemd/system/club.service`), que lo arranca al encender y lo
reinicia si cae:

```ini
[Unit]
Description=Club de Lectura (Gunicorn)
After=network.target

[Service]
User=www-data
WorkingDirectory=/srv/club
EnvironmentFile=/etc/club/club.env
ExecStart=/srv/club/venv/bin/gunicorn -c /etc/club/gunicorn.conf.py app:app
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now club
```

En ese caso Gunicorn escucha en `127.0.0.1:8000` y Nginx hace `proxy_pass http://127.0.0.1:8000;`. En Docker el
nombre del servicio (`app`) hace de dirección.

## 🩺 4. Cuando algo falla

Tres códigos que vas a ver mucho, y dónde mirar:

| Lo que ve el cliente | Qué significa | Dónde se ve |
|---|---|---|
| **404** Not Found | Nginx no conoce la app: busca un fichero que no existe | Falta `@app` en `try_files` |
| **502** Bad Gateway | La cocina **no contesta**: puerto mal en `proxy_pass` o la app caída | `logs/club_error.log` (Nginx) |
| **405** Method Not Allowed | La app existe, pero esa ruta no acepta ese método (p. ej. `POST`) | `logs/gunicorn-acceso.log` |
| **500** Internal Server Error | La app ha **reventado** al preparar la respuesta | `logs/gunicorn-errores.log` |

El 502, reproducido en el laboratorio con `proxy_pass http://app:8001;`:

```bash
docker compose exec cliente curl -sk -o /dev/null -w '%{http_code}\n' https://club.iaw.local/
# 502
tail -1 logs/club_error.log
# … connect() failed (111: Connection refused) while connecting to upstream, … upstream: "http://172.31.0.2:8001/"
```

!!! tip "Si la app no arranca"
    Un error de sintaxis en `app.py` tumba la app al reiniciarla, y Nginx devuelve **502**. Míralo así:
    `docker compose ps` (la app no sale como `running`) y `docker compose logs app` (el error de Python sale ahí).

## 🐍 5. Flask para administradores: leer el recetario

### 5.1 Las cuatro piezas de `app.py`

```python
app = Flask(__name__)                          # ① la aplicación
app.secret_key = os.environ["SECRET_KEY"]      #    la llave de las sesiones: sale del entorno, no del código

@app.route("/")                                # ② una ruta: qué URL atiende…
def inicio():                                  # ③ …y qué función la prepara
    return render_template("index.html", libros=LIBROS)   # ④ la respuesta: una plantilla con datos
```

| Pieza | Para qué |
|---|---|
| `@app.route("/ruta", methods=[…])` | Qué URL atiende la función y con qué métodos HTTP |
| La función | Prepara la respuesta. `request.form` tiene los datos de un formulario; `request.args`, los de la URL (`?q=…`) |
| `render_template("x.html", …)` | Rellena una plantilla de `templates/` con datos |
| `jsonify(…)` · `redirect(…)` · `abort(404)` | Responder en JSON, mandar a otra URL o devolver un error |

### 5.2 Los métodos: el 405

Una ruta, si no se dice otra cosa, solo acepta `GET`. Para recibir un formulario hace falta `POST`:

```python
@app.route("/recomendar", methods=["GET"])            # así viene: el formulario no se puede enviar
@app.route("/recomendar", methods=["GET", "POST"])    # así tiene que quedar
```

```bash
docker compose exec cliente curl -sk -d 'nombre=Ana&libro=Nada' https://club.iaw.local/recomendar | grep title
# <title>405 Method Not Allowed</title>
tail -1 logs/gunicorn-acceso.log
# 172.31.0.3 - - [30/Oct/2026:18:46:16 +0000] "POST /recomendar HTTP/1.0" 405 153 "-" "curl/8.14.1"
```

Después del cambio, `docker compose restart app` y el mismo `curl` responde `Gracias, Ana. Lo apuntamos.`

## 🛡️ 6. XSS en las plantillas

En la UD4 había que escapar a mano con `htmlspecialchars()`. Las plantillas de Flask (Jinja2) lo hacen solas: todo lo
que va entre `{{ }}` sale escapado. **Salvo que alguien escriba `|safe`**, que significa «confío en esto, no lo
escapes».

```html
<p class="nota">Gracias, {{ nombre|safe }}. Lo apuntamos.</p>   <!-- así viene: XSS -->
<p class="nota">Gracias, {{ nombre }}. Lo apuntamos.</p>        <!-- así tiene que quedar -->
```

Con `|safe`, un nombre como `<script>alert('hola')</script>` se ejecuta en el navegador de quien vea la página. Sin
`|safe`, sale como texto (esto es lo que llega en el código de la página):

```text
Gracias, &lt;script&gt;alert(1)&lt;/script&gt;. Lo apuntamos.
```

`|safe` solo se usa con HTML que has escrito tú, nunca con algo que viene del usuario.

## 🔐 7. Sesiones y `SECRET_KEY`

### 7.1 La pulsera

HTTP no recuerda nada entre una petición y la siguiente. Para saber que ya has entrado, la app te da una **cookie de
sesión**: una pulsera, como en un festival. En Flask la sesión va **dentro de la cookie**, firmada:

```bash
curl -sk -c /tmp/j -d 'usuario=ana&clave=club2026' https://club.iaw.local/entrar -o /dev/null -w '%{http_code}\n'
# 302                                                 ← entra y le manda a /socios
grep session /tmp/j | awk '{print $7}'
# eyJ1c3VhcmlvIjoiYW5hIn0.auTmCQ.DeBAGnJ4YpTQWRZbxFDl6qX_AeY
echo eyJ1c3VhcmlvIjoiYW5hIn0 | base64 -d
# {"usuario":"ana"}                                   ← se puede LEER
```

Tiene tres partes: los datos (en base64, **no cifrados**), la fecha y el **sello** (una firma hecha con la
`SECRET_KEY`). Si alguien cambia `ana` por `admin`, el sello ya no cuadra y Flask la rechaza. Se puede leer, pero no
falsificar. Por eso en la sesión **nunca** se guardan contraseñas ni datos privados.

### 7.2 La puerta de los socios

Que exista el login no protege nada si la página no lo comprueba. Así viene `/socios`: entra cualquiera y ve
«Hola, ¿?». La comprobación va al principio de la función:

```python
@app.route("/socios")
def socios():
    if "usuario" not in session:                  # sin pulsera, a la puerta
        return redirect(url_for("entrar"))
    …
```

```bash
docker compose exec cliente curl -sk -o /dev/null -w '%{http_code} %{redirect_url}\n' https://club.iaw.local/socios
# 302 https://club.iaw.local/entrar
```

### 7.3 El sello del club: la `SECRET_KEY`

Quien conozca la `SECRET_KEY` puede **fabricar pulseras** de cualquier usuario. Por eso:

- larga y al azar (32 caracteres o más). Se genera así:

    ```bash
    docker compose exec app python3 -c "import secrets; print(secrets.token_hex(32))"
    # f0d22525905a4a16dc173b532539ddd85cb3ee41462504ef82ec1cca89c6039c   (cada vez sale otra)
    ```

- en una **variable de entorno** (`config/club.env`), nunca escrita en `app.py`;
- **nunca en Git**: `club.env` va en el `.gitignore` (lo veremos en la UD6);
- si se filtra, se cambia: todas las sesiones abiertas dejan de valer.

### 9.1 Depuración apagada

Con `FLASK_DEBUG=1`, cuando la app revienta enseña la **traza con el código** y una **consola de depuración** que

```text
    return f"Terminarás en {LIBROS[0]['paginas'] / paginas_por_dia} días"
ZeroDivisionError: division by zero
```

### 9.2 Cuántos cocineros: los workers

Cada worker de Gunicorn atiende **una petición a la vez**. Con uno solo, si una petición tarda, las demás esperan.
La regla de la documentación de Gunicorn es:

**workers = 2 × núcleos + 1**

El servidor de producción del Club tiene **2 CPU** → 2 × 2 + 1 = **5 workers**. Igual que con `pm.max_children` en la
UD4, hay que comprobar que caben en memoria: 5 workers × lo que ocupa cada uno (`ps`, columna RSS) tiene que ser menor
que la memoria libre.

```python
# config/gunicorn.conf.py
workers = 5                    # el servidor tiene 2 CPU → 2 × 2 + 1 = 5
```

```bash
docker compose exec app ps -o pid,args -C gunicorn
#   PID COMMAND
#     1 … gunicorn -c /lab/config/gunicorn.conf.py app:app     ← el jefe (no atiende peticiones)
#     8 … gunicorn -c /lab/config/gunicorn.conf.py app:app     ← worker 1
#   …                                                           (6 líneas: el jefe y 5 workers)
```

!!! note "¿Por qué no `nproc`?"
    Dentro del contenedor, `nproc` cuenta las CPU **de tu ordenador** (16 en el del aula), no las del servidor de
    producción. Se calcula con las del servidor donde va a funcionar.

| | PHP-FPM (UD4) | Gunicorn (UD5) |
|---|---|---|
| Procesos que atienden | `pm.max_children` | `workers` |
| Se calcula con | La memoria | Las CPU (y se comprueba la memoria) |
| Fichero | `zz-lab-pool.conf` | `gunicorn.conf.py` |
| Aplicar | `docker compose restart php` | `docker compose restart app` |

## ❓ 11. Casos prácticos y autoevaluación

1. **Has corregido un fallo en `app.py`, pero la web sigue fallando igual. ¿Qué pasa?**
    ??? success "Respuesta"
        Gunicorn cargó el código al arrancar y sigue con el antiguo en memoria. Hay que reiniciar la app
        (`docker compose restart app` o `systemctl restart`). Con PHP no pasaba: lee el `.php` en cada petición.

2. **La portada da 404, pero `estilo.css` se ve bien. ¿Qué falta en Nginx?**
    ??? success "Respuesta"
        Que mande a la app lo que no es un fichero: `try_files $uri @app;` y el bloque `location @app` con
        `proxy_pass`. Sin eso, Nginx busca un fichero llamado así y no lo encuentra.

3. **Todas las páginas dan 502. ¿Qué dos cosas miras primero?**
    ??? success "Respuesta"
        El puerto o el nombre de `proxy_pass` (en `club_error.log`, `connect() failed (111: Connection refused)`) y si
        la app está viva (`docker compose ps` y `docker compose logs app`: un error de Python la tumba).

4. **Los logs de la app dicen que todos los visitantes tienen la misma IP, una privada. ¿Por qué?**
    ??? success "Respuesta"
        Es la IP de Nginx. Faltan `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` en Nginx y que la
        app se fíe de esa cabecera (`ProxyFix`).

5. **Un compañero dice que la cookie de sesión «está cifrada, así que se puede guardar ahí el DNI». ¿Tiene razón?**
    ??? success "Respuesta"
        No. Está **firmada**, no cifrada: cualquiera la lee con `base64 -d`. Lo que no puede es modificarla sin la
        `SECRET_KEY`. En la sesión, solo un identificador.

6. **La `SECRET_KEY` está escrita en `app.py` y el repositorio es público. ¿Qué riesgo hay y qué haces?**
    ??? success "Respuesta"
        Cualquiera puede fabricar cookies de sesión válidas y entrar como otro usuario. Se genera una nueva, se pasa
        a una variable de entorno fuera de Git y se reinicia la app (todas las sesiones antiguas dejan de valer).

7. **Al provocar un error, el navegador enseña el código y una consola. ¿Qué está mal configurado?**
    ??? success "Respuesta"
        `FLASK_DEBUG=1`. En un servidor tiene que ser 0: la consola permite ejecutar Python en el servidor.

8. **El servidor de producción tiene 4 CPU. ¿Cuántos workers de Gunicorn pondrías y qué compruebas antes?**
    ??? success "Respuesta"
        2 × 4 + 1 = 9. Antes, que 9 workers caben en la memoria libre (lo que ocupa cada uno, en `ps`, por 9).

## 📋 12. Glosario rápido de repaso

| Término | Definición |
|---|---|
| **Flask** | Librería de Python para hacer aplicaciones web: rutas, plantillas, sesiones |
| **Gunicorn** | Servidor de aplicaciones para Python: arranca varios workers con la app y les reparte las peticiones |
| **WSGI** | Estándar con el que un servidor de aplicaciones (Gunicorn) le pasa las peticiones a una app Python (PEP 3333) |
| **Worker** | Proceso de Gunicorn que atiende una petición a la vez |
| **`proxy_pass`** | Directiva de Nginx que reenvía la petición a otro servidor HTTP (aquí, Gunicorn) |
| **`try_files $uri @app`** | Si el fichero existe, lo sirve Nginx; si no, salta a la *location* `@app` |
| **`X-Forwarded-For`** | Cabecera con la IP original del cliente, que añade el proxy |
| **`X-Forwarded-Proto`** | Cabecera que dice si el cliente entró por `http` o `https` |
| **Ruta** | URL que atiende una función de Flask (`@app.route`) |
| **405** | Method Not Allowed: la ruta existe, pero no acepta ese método |
| **502** | Bad Gateway: el proxy no consigue respuesta del servidor de detrás |
| **Plantilla (Jinja2)** | HTML con huecos `{{ }}` que Flask rellena; escapa el contenido solo |
| **`|safe`** | Filtro de Jinja2 que desactiva el escape: con datos del usuario, XSS |
| **Sesión** | Forma de recordar a un usuario entre peticiones; en Flask, una cookie firmada |
| **`SECRET_KEY`** | Llave con la que se firman las cookies de sesión; secreta, larga y fuera del código |
| **API (JSON)** | Respuesta pensada para otro programa, con `Content-Type: application/json` |
| **`FLASK_DEBUG`** | Modo depuración: enseña el código y una consola al fallar. En producción, 0 |
| **Variable de entorno** | Valor que recibe un programa al arrancar (`club.env`), fuera del código |
| **venv** | Entorno virtual de Python: las librerías de una app, aisladas del sistema |
