## 📖 0. Fundamentos: la despensa

### 0.1 El problema

Hasta ahora los datos del Club vivían **dentro del programa** (`LIBROS = [...]` en `app.py`). Eso tiene tres problemas:

- si la app se reinicia, **lo nuevo se pierde** (las recomendaciones de la UD5 desaparecían con cada `restart`);
- con varios workers, **cada uno tiene su copia** (en la batería de la UD5: una reserva solo la veía un worker);
- dos programas distintos (la web en PHP y la API en Python) **no pueden compartirlos**.

Hace falta un sitio aparte, que guarde los datos en disco y al que le pidan todos: un **sistema gestor de bases de
datos** (SGBD).

| En el restaurante | En el servidor |
|---|---|
| La cocina | PHP-FPM y Gunicorn: preparan la página |
| **La despensa** | **MariaDB**: guarda los ingredientes (los datos) y se los da a quien tenga permiso |
| El libro de recetas | **Git**: la configuración del servidor, con todas sus versiones |

### 0.2 MariaDB

**MariaDB** es un SGBD relacional (los datos van en **tablas**: filas y columnas) que se maneja con **SQL**. Es la
continuación libre de MySQL: se instala igual, se usa igual y los programas se conectan a él igual. Es lo que usan
WordPress, Moodle o Nextcloud (lo veremos en el 2.º trimestre).

## ⚙️ 1. MariaDB como servicio

### 1.1 Un servidor aparte

MariaDB es **otro servidor**: un programa que escucha en el **puerto 3306** y al que los demás se conectan con usuario y
contraseña.

**La base de datos nunca se ve desde fuera**: solo desde la red interna, como los Apache de la UD3 o el PHP de la UD4.
Si el puerto 3306 está abierto a internet, alguien probará contraseñas antes de una hora.

### 1.2 Entrar

El cliente de MariaDB se llama `mariadb` (antes, `mysql`). **Como administrador (`root`) se entra desde el propio
servidor de base de datos**:

```bash
docker compose exec db mariadb -u root -p          # pide la contraseña de root
```

Unas órdenes para mirar (terminan en `;`):

```sql
SHOW DATABASES;            -- las bases de datos
USE club;                  -- trabajar con la base «club»
SHOW TABLES;               -- sus tablas
SELECT id, usuario, email FROM socios;
EXIT;
```

Salida real del laboratorio:

```text
+--------------------+       +----------------+       +----+---------+----------------------+
| Database           |       | Tables_in_club |       | id | usuario | email                |
+--------------------+       +----------------+       +----+---------+----------------------+
| club               |       | socios         |       |  1 | ana     | ana@club.iaw.local   |
| information_schema |       +----------------+       |  2 | luis    | luis@club.iaw.local  |
| mysql              |                                |  3 | marta   | marta@club.iaw.local |
| performance_schema |                                +----+---------+----------------------+
| sys                |
+--------------------+
```

`information_schema`, `mysql`, `performance_schema` y `sys` son del propio MariaDB: **no se tocan**. En `mysql` están
los usuarios y sus permisos.

### 1.3 En un servidor Debian (sin Docker)

```bash
sudo apt install mariadb-server
sudo mariadb-secure-installation      # contraseña de root, quita usuarios anónimos y root remoto, borra la base «test»
sudo mariadb                          # en Debian, root entra sin contraseña… pero solo desde la propia máquina (unix_socket)
```

otra máquina, se cambia a la IP de la red interna, **nunca** a `0.0.0.0` con el puerto abierto.

## 🗃️ 2. SQL justo para administrar

No vamos a diseñar bases de datos (eso es de DAW). Con cuatro órdenes un administrador se apaña:

```sql
CREATE TABLE libros (
  id      INT AUTO_INCREMENT PRIMARY KEY,   -- un número que pone MariaDB solo: 1, 2, 3…
  titulo  VARCHAR(150) NOT NULL,            -- texto de hasta 150 caracteres, obligatorio
  autor   VARCHAR(100) NOT NULL,
  anio    SMALLINT     NOT NULL,            -- número entero pequeño
  paginas SMALLINT     NOT NULL
);

INSERT INTO libros (titulo, autor, anio, paginas) VALUES
  ('El camino', 'Miguel Delibes', 1950, 224),
  ('Nada', 'Carmen Laforet', 1945, 320),
  ('Luces de bohemia', 'Valle-Inclán', 1924, 160),
  ('La casa de los espíritus', 'Isabel Allende', 1982, 448);
-- Query OK, 4 rows affected (0.001 sec)

SELECT * FROM libros;
```

```text
+----+---------------------------+----------------+------+---------+
| id | titulo                    | autor          | anio | paginas |
+----+---------------------------+----------------+------+---------+
|  1 | El camino                 | Miguel Delibes | 1950 |     224 |
|  2 | Nada                      | Carmen Laforet | 1945 |     320 |
|  3 | Luces de bohemia          | Valle-Inclán   | 1924 |     160 |
|  4 | La casa de los espíritus  | Isabel Allende | 1982 |     448 |
+----+---------------------------+----------------+------+---------+
```

| Orden | Para qué | Ejemplo |
|---|---|---|
| `CREATE TABLE` | Crear una tabla con sus columnas | arriba |
| `INSERT INTO … VALUES` | Añadir filas | arriba |
| `SELECT … FROM … WHERE … ORDER BY` | Leer | `SELECT titulo FROM libros WHERE anio < 1950 ORDER BY anio;` |
| `UPDATE … SET … WHERE` | Cambiar filas | `UPDATE libros SET paginas = 230 WHERE id = 1;` |
| `DELETE FROM … WHERE` | Borrar filas | `DELETE FROM libros WHERE id = 4;` |

!!! danger "El `UPDATE` sin `WHERE`"
    `UPDATE libros SET titulo = '???';` **sin `WHERE`** cambia **todas** las filas. Salida real:

    ```text
    +----+--------+
    | id | titulo |
    +----+--------+
    |  1 | ???    |
    |  2 | ???    |
    |  3 | ???    |
    |  4 | ???    |
    +----+--------+
    ```

    No hay papelera ni «deshacer». Lo único que te salva es **una copia de seguridad** (bloque 10).

## 👤 3. Usuarios y permisos: cada uno, lo justo

### 3.1 La aplicación nunca entra como root

`root` puede hacerlo todo: borrar bases de datos, crear usuarios, leer todas las tablas. Si la web entra como `root` y
alguien consigue colarle una orden (bloque 7), **esa orden se ejecuta como root**. La regla es el **mínimo privilegio**:
un usuario para cada aplicación, con permiso **solo** en su base de datos y **solo** para lo que necesita.

```sql
CREATE USER 'club_app'@'%' IDENTIFIED BY 'una-contraseña-larga';   -- el usuario de la aplicación
GRANT SELECT, INSERT, UPDATE ON club.* TO 'club_app'@'%';         -- leer, añadir y cambiar en «club»; nada más
SHOW GRANTS FOR 'club_app'@'%';
```

```text
| GRANT USAGE ON *.* TO `club_app`@`%` IDENTIFIED BY PASSWORD '*4BBC30FFB815AE8AA6C5AD8D3E63D751D29C1409' |
| GRANT SELECT, INSERT, UPDATE ON `club`.* TO `club_app`@`%`                                              |
```

- `'club_app'@'%'`: un usuario es **nombre + desde dónde**. `%` = desde cualquier máquina (en la red interna);
  `'localhost'` = solo desde el propio servidor; `'192.168.1.%'` = desde esa red.
- `club.*`: todas las tablas de la base `club`. `*.*` sería **todas las bases**: nunca para una aplicación.
- `USAGE` significa «puede conectarse, sin permisos». La contraseña se guarda como hash.
- Para quitar un permiso: `REVOKE UPDATE ON club.* FROM 'club_app'@'%';`. Para borrar el usuario: `DROP USER`.

Desde el ordenador del administrador, `club_app` puede leer y cambiar, pero no borrar:

```bash
docker compose exec admin mariadb -h db -u club_app -p club -e "DROP TABLE libros"
# ERROR 1142 (42000) at line 1: DROP command denied to user 'club_app'@'192.168.32.4' for table `club`.`libros`
docker compose exec admin mariadb -h db -u club_app -p club -e "DELETE FROM libros"
# ERROR 1142 (42000) at line 1: DELETE command denied to user 'club_app'@'192.168.32.4' for table `club`.`libros`
```

!!! note "Las líneas `--------------`"
    El cliente de `admin` repite la orden entre dos líneas de guiones antes del resultado. Es normal.

### 3.2 Root, solo en casa

La imagen de MariaDB crea `root@'%'`: root puede entrar **desde cualquier sitio**. Se mira y se quita:

```sql
SELECT User, Host FROM mysql.user;
DROP USER 'root'@'%';            -- root sigue existiendo como 'root'@'localhost'
```

```text
| User        | Host      |          | User        | Host      |
| root        | %         |   ───▶   | club_app    | %         |
| root        | localhost |          | root        | localhost |
```

Desde `admin`, root ya no entra; desde dentro del servidor (`docker compose exec db mariadb -u root -p`), sí:

```text
ERROR 1045 (28000): Access denied for user 'root'@'192.168.32.4' (using password: YES)
```

!!! warning "Y la web se cae"
    En el laboratorio, la web entraba como root desde otra máquina. Al quitar `root@'%'`, `libros.php` da
    `1045 Access denied for user 'root'@…`. No es un fallo: es la prueba de que **la web no tenía que usar root**. Se
    arregla en la sesión 2, con `club_app`.

## 🔌 5. La cocina pide a la despensa: conectar las aplicaciones

### 5.1 PHP: PDO

**PDO** es la forma estándar de PHP de hablar con bases de datos. Se conecta con un **DSN** (*Data Source Name*): una
cadena que dice qué tipo de base de datos, dónde está, cuál y en qué juego de caracteres.

```php
$dsn = 'mysql:host=db;dbname=club;charset=utf8mb4';            // MariaDB habla el mismo «idioma» que MySQL
$pdo = new PDO($dsn, $usuario, $clave, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,      // si algo falla, que avise
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,            // cada fila, un array con los nombres de columna
]);
$libros = $pdo->query('SELECT titulo, autor, anio FROM libros ORDER BY anio')->fetchAll();
```

En Debian, la extensión es el paquete `php-mysql`. En el laboratorio ya está (`docker-php-ext-install pdo_mysql`).

### 5.2 Python: PyMySQL

```python
import pymysql
c = pymysql.connect(host="db", database="club", user=usuario, password=clave,
                    charset="utf8mb4", cursorclass=pymysql.cursors.DictCursor)   # cada fila, un diccionario
with c.cursor() as cur:
    cur.execute("SELECT titulo, autor, anio, paginas FROM libros ORDER BY anio")
    filas = cur.fetchall()
```

Las dos piden lo mismo: **dónde (host), qué base, quién (usuario) y con qué contraseña**. La web del laboratorio enseña
con qué usuario está conectada (`SELECT CURRENT_USER()`):

```text
Lecturas del trimestre (4)
  Luces de bohemia — Valle-Inclán (1924)
  Nada — Carmen Laforet (1945)
  El camino — Miguel Delibes (1950)
  La casa de los espíritus — Isabel Allende (1982)
Conectado a la base de datos como: club_app@%
```

## 🔐 6. Los secretos, fuera del código

En el estado inicial, `db.php` lleva la contraseña de root **escrita en el código**. El código acaba en Git, en un
pendrive o en la pantalla del proyector. Las contraseñas van en un **fichero de configuración aparte**, que:

- está **fuera de la carpeta de la web** (nadie lo puede pedir por URL);
- **no va a Git** (`.gitignore`, bloque 11);
- solo lo puede leer el usuario del servicio (`chmod 640`, propietario `www-data`, en un servidor de verdad).

En el Club es `servidor/club.env`, el mismo para PHP y para Python:

```ini
DB_HOST=db
DB_NAME=club
DB_USER=club_app
DB_PASS=…
```

| Quién | Cómo lo lee | Si lo cambias |
|---|---|---|
| PHP (`db.php`) | La función 👀 `leer_env('/etc/club/club.env')`, en cada petición | Se nota al recargar |
| Python (la API) | `os.environ["DB_PASS"]`: el script de arranque carga el fichero | `docker compose restart app` (lo de la UD5) |

```php
$cfg = leer_env('/etc/club/club.env');
$dsn = "mysql:host={$cfg['DB_HOST']};dbname={$cfg['DB_NAME']};charset=utf8mb4";
return new PDO($dsn, $cfg['DB_USER'], $cfg['DB_PASS'], [ … ]);
```

## 💉 7. Inyección SQL y consultas preparadas

### 7.1 El ataque

El buscador del Club **pega** lo que escribe el usuario dentro del SQL:

```php
$sql = "SELECT titulo, autor, anio FROM libros WHERE titulo LIKE '%$q%'";
```

Si alguien busca `x' UNION SELECT usuario, clave, email FROM socios -- -`, la consulta que llega a MariaDB es:

```sql
SELECT titulo, autor, anio FROM libros WHERE titulo LIKE '%x'
UNION SELECT usuario, clave, email FROM socios -- -%'
```

La comilla cierra el texto, `UNION` añade **otra consulta** y `--` convierte el resto en un comentario. Salida real del
buscador:

```text
ana — $2y$10$Hc8vZbXq4m1Yw0tPpQ7NeuXr8m6sJk2bQ9dW1aF3gT5yU7iO9pL2e (ana@club.iaw.local)
luis — $2y$10$Rk2pL9sD4fG6hJ8kL0zX1cV3bN5mQ7wE9rT1yU3iO5pA7sD9fG1hJ (luis@club.iaw.local)
marta — $2y$10$Zx9cV7bN5mQ3wE1rT9yU7iO5pA3sD1fG9hJ7kL5zX3cV1bN9mQ7wE (marta@club.iaw.local)
```

Los socios, sus correos y los hashes de sus contraseñas, en un buscador de libros. Fíjate: **funciona igual con
`club_app`**, porque tiene `SELECT` en `club.*`. El mínimo privilegio limita el daño (no puede hacer `DROP`), pero
**no evita la inyección**. Es la vulnerabilidad A03 del OWASP Top 10.

### 7.2 La solución: consultas preparadas

El SQL se manda **con un hueco** (`?`) y el texto del usuario va **aparte**. MariaDB nunca lo mezcla con la orden: lo
trata siempre como un dato.

```php
$st = $pdo->prepare('SELECT titulo, autor, anio FROM libros WHERE titulo LIKE ?');
$st->execute(['%' . $q . '%']);
$resultado = $st->fetchAll();
```

```python
cur.execute("SELECT titulo, autor, anio FROM libros WHERE titulo LIKE %s", ("%" + q + "%",))   # PyMySQL: %s, aparte
```

Con la consulta preparada, el mismo ataque da **0 resultados** (busca un libro que se llame literalmente así), y
`?q=Nada` sigue encontrando *Nada*.

| | Lo que hace | ¿Evita la inyección? |
|---|---|---|
| Consulta preparada | El dato va aparte del SQL | ✅ Sí |
| Usuario con lo justo | Limita lo que puede hacer una orden colada | Limita el daño |
| `htmlspecialchars()` | Evita XSS al imprimir (UD4) | ❌ No: es otro problema |
| «Validar» quitando comillas a mano | Siempre hay otra forma de colarla | ❌ No |

## 🩺 8. Cuando la conexión falla

Los errores de MariaDB llevan un **número**. Con cuatro te apañas (salidas reales de `libros.php`, cambiando
`club.env`):

| Número | Mensaje (resumido) | Qué pasa |
|---|---|---|
| **2002** | `getaddrinfo for dbx failed` / `Connection refused` | No llega al servidor: `DB_HOST` mal, MariaDB parado o el 3306 cerrado |
| **1045** | `Access denied for user 'club_app'@'192.168.32.5' (using password: YES)` | Usuario o contraseña mal. `using password: NO` = **no ha mandado contraseña** (`DB_PASS` vacío) |
| **1044** | `Access denied for user 'club_app'@'%' to database 'biblioteca'` | La contraseña es buena, pero **no tiene permiso en esa base** (`DB_NAME` mal o falta el `GRANT`) |
| **1142** | `DROP command denied to user 'club_app'@…` | Conectado, pero **esa orden** no la tiene permitida |
| **1146** | `Table 'club.libros' doesn't exist` | Conectado, pero la tabla no existe |

En la API (Python), el usuario ve un 500 y el detalle va al log de Gunicorn:

```text
pymysql.err.OperationalError: (1045, "Access denied for user 'club_app'@'192.168.32.3' (using password: NO)")
```

!!! warning "Y el error en pantalla"
    `libros.php` enseña el error entero (la ruta del fichero, el usuario…) porque el PHP del laboratorio tiene
    `display_errors` encendido. En producción, apagado (UD4, bloque 7).

## 💾 10. Copias de seguridad

### 10.1 `mysqldump` y restaurar

`mysqldump` (o `mariadb-dump`) escribe **las órdenes SQL que vuelven a crear la base**: los `CREATE TABLE` y los
`INSERT` con todos los datos. Es texto: se lee, se comprime y se guarda donde quieras.

```bash
mysqldump -h db -u club_app -p --single-transaction --no-tablespaces club > /copias/club.sql
```

| Opción | Para qué |
|---|---|
| `--single-transaction` | Una foto coherente de la base sin bloquear las tablas (la web sigue funcionando) |
| `--no-tablespaces` | No copia información interna de almacenamiento. En MySQL 8, sin ella, pide el permiso `PROCESS`, que `club_app` no tiene; en MariaDB no hace falta, pero así la misma orden vale en los dos |

```text
-- MariaDB dump 10.19-11.8.6-MariaDB, for debian-linux-gnu (x86_64)
--
-- Host: db    Database: club
…
CREATE TABLE `libros` (
…
INSERT INTO `libros` VALUES
(1,'El camino','Miguel Delibes',1950,224),
…
```

**Restaurar** es pasarle ese fichero al cliente. Lo hace root, dentro del servidor, porque la copia empieza con
`DROP TABLE` y `CREATE TABLE`, que `club_app` no puede hacer:

```bash
docker compose exec -T admin cat /copias/club-20261030-191117.sql | docker compose exec -T db mariadb -u root -p'…' club
```

La contraseña de root va **pegada** a `-p`: con una tubería (`|`), el cliente no te la puede preguntar.

Después del `UPDATE` sin `WHERE` del bloque 2, restaurar la copia deja los cuatro títulos como estaban.

!!! danger "Una copia que no se ha restaurado nunca no es una copia"
    El día que la necesitas descubres que estaba vacía, o que le faltaba una tabla. Se prueba a restaurar **en otra base**
    (`CREATE DATABASE club_prueba` y se restaura ahí). Es lo que hace el comprobador del laboratorio.

### 10.2 Un script de copia

Lo que se hace a mano, se olvida. Se escribe un script que **no lleva contraseñas** (las lee de `club.env`) y pone la
fecha en el nombre:

```sh
#!/bin/sh
set -e
. /srv/servidor/club.env
FECHA=$(date +%Y%m%d-%H%M%S)
mysqldump -h "$DB_HOST" -u "$DB_USER" -p"$DB_PASS" --single-transaction --no-tablespaces "$DB_NAME" \
    > "/copias/club-$FECHA.sql"
find /copias -name 'club-*.sql' -mtime +7 -delete      # se guardan 7 días
echo "Copia hecha: /copias/club-$FECHA.sql"
```

```text
Copia hecha: /copias/club-20261030-191117.sql
```

En un servidor, lo lanza **cron** cada noche (`crontab -e`):

```text
30 3 * * * /srv/servidor/copia.sh          # a las 3:30, todos los días
```

Y la copia **no se queda en el mismo servidor**: si se rompe el disco, se pierden los datos y la copia. La estrategia
completa (dónde, cuántas, cifradas) se ve en SAD.

## 🌿 11. Git para la configuración del servidor

### 11.1 Por qué

Cambias `club.conf`, la web deja de ir y no recuerdas qué tocaste. Con **Git**, cada versión de la configuración queda
guardada con quién la cambió, cuándo y por qué, y se puede **ver la diferencia** y **volver atrás**. Lo usaste en DAW
para código; aquí, para la carpeta de configuración del servidor (`/etc/nginx`, scripts, etc.).

### 11.2 Empezar

```bash
docker compose exec admin bash          # dentro de /srv/servidor
git init
git config user.name "Ana Admin"; git config user.email ana@club.iaw.local
git status --short
```

```text
?? club.env          ← ¡con la contraseña dentro!
?? copia.sh
?? nginx/
```

### 11.3 `.gitignore`: los secretos, fuera

Antes del primer `git add`, un fichero `.gitignore` con lo que **nunca** debe entrar en el repositorio:

```text
club.env
*.key
```

```bash
git status --short          # ya no sale club.env
git add -A
git commit -m "Configuración del servidor del Club"
git ls-files                # .gitignore · copia.sh · nginx/club.conf
git check-ignore -v club.env
# .gitignore:1:club.env	club.env
```

!!! danger "Si una contraseña llega a Git, ya está en el historial"
    Borrar el fichero en el commit siguiente **no la quita**: sigue en los commits anteriores, y en todas las copias del
    repositorio. Lo único seguro es **cambiar la contraseña**. Por eso el `.gitignore` va primero.

### 11.4 Ver qué cambió y volver atrás

Alguien quita un `;` en `club.conf`:

```bash
docker compose exec nginx nginx -t
# [emerg] invalid number of arguments in "fastcgi_pass" directive in /etc/nginx/sites-enabled/club.conf:30
git status --short          #  M nginx/club.conf
git diff
```

```diff
     location ~ \.php$ {
         try_files $uri =404;
-        fastcgi_pass php:9000;
+        fastcgi_pass php:9000
         include fastcgi_params;
```

| Para… | Orden |
|---|---|
| Deshacer un cambio **sin commit** | `git restore nginx/club.conf` |
| Ver el historial | `git log --oneline` |
| Deshacer un **commit** ya hecho, dejando constancia | `git revert HEAD` (crea un commit nuevo que lo deshace) |

```text
7a97c14 Revert "Copia sin --single-transaction"
6cfd615 Copia sin --single-transaction
5636071 Configuración del servidor del Club
```

`git revert` no borra la historia: añade un commit que deshace el anterior. En un servidor compartido es lo correcto: se
sabe qué pasó.

## ❓ 13. Casos prácticos y autoevaluación

1. **La web de una empresa se conecta a MariaDB con root. ¿Qué le dices y qué harías?**
    ??? success "Respuesta"
        Que una orden colada por la web (inyección) se ejecutaría como root: podría borrar todas las bases o crear
        usuarios. Se crea un usuario para esa aplicación con permiso solo en su base y solo `SELECT`, `INSERT` y
        `UPDATE` (lo que necesite), y la web pasa a usarlo.

2. **`Access denied for user 'club_app'@'172.18.0.5' (using password: NO)`. ¿Qué pasa?**
    ??? success "Respuesta"
        Error 1045, y `using password: NO`: la aplicación no ha mandado contraseña. La variable de la contraseña está
        vacía o no se ha cargado (en Python: ¿se reinició la app después de cambiar el `.env`?).

3. **Con el usuario y la contraseña bien sale `1044 … to database 'tienda'`. ¿Qué falta?**
    ??? success "Respuesta"
        El permiso en esa base: `GRANT … ON tienda.* TO …`. O la aplicación apunta a una base que no es la suya.

4. **¿Por qué `GRANT ALL ON *.*` a la aplicación es mala idea, aunque «así funciona seguro»?**
    ??? success "Respuesta"
        Le da todos los permisos sobre **todas** las bases (también `mysql`, con los usuarios). Cualquier fallo de la
        aplicación se convierte en el control total del servidor de base de datos.

5. **Un buscador hace `"… WHERE nombre = '$q'"`. ¿Qué cambiarías? ¿Basta con quitar las comillas de `$q`?**
    ??? success "Respuesta"
        Consulta preparada: `prepare("… WHERE nombre = ?")` y `execute([$q])`. Quitar comillas a mano no basta: hay
        otras formas de colar SQL. Con la consulta preparada, el dato nunca se mezcla con la orden.

6. **Has subido `club.env` a GitHub y te das cuenta al día siguiente. Lo borras y haces commit. ¿Ya está?**
    ??? success "Respuesta"
        No: la contraseña sigue en el historial y en las copias del repositorio. Hay que **cambiar la contraseña** en
        MariaDB y en `club.env`, y añadir `club.env` al `.gitignore`.

7. **Tienes copias de la base cada noche desde hace un año, pero nunca has restaurado ninguna. ¿Qué harías hoy?**
    ??? success "Respuesta"
        Restaurar la última en una base de prueba y comprobar que están todas las tablas y los datos. Una copia que no
        se ha probado puede estar vacía o incompleta.

8. **Alguien cambió la configuración de Nginx hace dos días y desde entonces falla una página. Está en Git. ¿Cómo lo
   investigas y lo arreglas?**
    ??? success "Respuesta"
        `git log --oneline` para ver los commits de esos días, `git show` o `git diff` para ver qué cambió, y
        `git revert` del commit culpable (queda constancia). Después, `nginx -t` y recargar.

## 📋 14. Glosario rápido de repaso

| Término | Definición |
|---|---|
| **SGBD** | Sistema gestor de bases de datos: el servidor que guarda los datos y se los da a quien tenga permiso |
| **MariaDB** | SGBD relacional libre, continuación de MySQL. Puerto 3306 |
| **Tabla** | Datos en filas (registros) y columnas (campos) |
| **SQL** | Lenguaje para crear tablas y leer o cambiar datos (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) |
| **`root`** | El administrador de MariaDB: puede hacerlo todo. Solo desde el propio servidor |
| **`'usuario'@'host'`** | Un usuario de MariaDB es nombre + desde dónde se conecta (`%` = desde cualquier sitio) |
| **`GRANT` / `REVOKE`** | Dar o quitar permisos a un usuario sobre una base o una tabla |
| **Mínimo privilegio** | Cada usuario, solo los permisos que necesita y solo donde los necesita |
| **PDO** | La forma estándar de PHP de conectarse a una base de datos |
| **DSN** | La cadena que dice a qué base conectarse: `mysql:host=db;dbname=club;charset=utf8mb4` |
| **PyMySQL** | Librería de Python para conectarse a MariaDB/MySQL |
| **Inyección SQL** | Colar órdenes SQL a través de un dato que la aplicación pega dentro de una consulta |
| **Consulta preparada** | El SQL va con huecos (`?`, `%s`) y los datos aparte: nunca se mezclan |
| **`mysqldump`** | Programa que escribe en un fichero las órdenes SQL para volver a crear una base con sus datos |
| **Restaurar** | Ejecutar ese fichero en una base para recuperar los datos |
| **cron** | Servicio de Linux que lanza tareas a una hora (`crontab -e`) |
| **Git** | Sistema de control de versiones: guarda cada versión de unos ficheros, con quién, cuándo y por qué |
| **commit** | Una versión guardada en Git, con su mensaje |
| **`.gitignore`** | Lista de ficheros que Git no debe guardar nunca (secretos, logs) |
| **`git diff` / `restore` / `revert`** | Ver qué cambió / deshacer lo que no tiene commit / deshacer un commit con otro commit |
